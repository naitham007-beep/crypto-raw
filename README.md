# crypto-raw — คลังข้อมูลดิบตลาดคริปโต (BTC · ETH)

เก็บ snapshot ตลาดทุก 2 ชั่วโมงด้วย GitHub Actions แล้ว commit กลับเข้า repo นี้
เป้าหมาย: **เป็นเจ้าของข้อมูลเอง ไม่ผูกกับสถานะสมาชิกของเว็บใคร**

> ⏰ **ทำไมต้องรีบเริ่ม:** ทุกอย่างในนี้ดึงย้อนหลังได้ **ยกเว้น IV (ค่าความผันผวนที่ตลาดคิด) — ย้อนไม่ได้**
> ไม่เก็บวันนี้ = หายถาวร · ต้องสะสม 1–3 เดือนกว่าจะมีเส้น baseline ไว้เทียบว่า "แพง/ถูก" คืออะไร

## 🔑 กฎเหล็กของคลังนี้
**เก็บ response ดิบทั้งก้อน ห้ามเก็บแค่เลขที่คำนวณแล้ว**
เก็บแค่ "max pain = 79,000" แล้ววันหลังพบว่าสูตรผิด → ข้อมูลหลายเดือนใช้ไม่ได้ ย้อนไม่ได้
เก็บดิบไว้ → สูตรผิดกี่รอบก็คำนวณใหม่ได้ · ค่าที่จ่ายคือพื้นที่วันละ 3 MB เท่านั้น

## 📦 เก็บอะไรบ้าง (16 endpoint · ไม่ต้องใช้ API key สักตัว)
| กลุ่ม | แหล่ง | ใช้ทำอะไร |
|---|---|---|
| ราคา + index | Binance, OKX | ตรึงเวลาให้ snapshot · อ้างอิงราคาขณะเก็บ |
| funding (ปัจจุบัน + ย้อนหลัง 20 รอบ) | OKX | ต้นทุนถือสถานะ · ดูว่าฝั่งไหนแออัด |
| open interest (perp) | OKX | สถานะค้างในตลาด เพิ่ม/ลด |
| **options: IV + greeks รายสัญญา** | OKX `opt-summary` | IV surface · 25ΔRR · GEX / โซนตรึง |
| **options: OI รายstrike** | OKX | max pain · กำแพง put/call |
| options (แหล่งสำรอง) | Deribit | cross-check และใช้แทนเวลา OKX ล่ม |

**ไม่เก็บ klines** เพราะ Binance ให้ย้อนหลังเป็นปีอยู่แล้ว — RSI / EMA / ATR percentile คำนวณย้อนหลังได้ตลอด

## 🗂️ โครงสร้างไฟล์
```
raw/2026/09/10/1405Z/okx_optsum_btc.json.xz     ← response ดิบ บีบด้วย xz
raw/2026/09/10/1405Z/_meta.json                 ← ผลการดึงรอบนั้น (สำเร็จ/ล้ม/ขนาด/sha256/ms)
status/last_run.json                            ← สถานะล่าสุด เปิดดูเร็วๆ ว่าตัวเก็บยังไหวอยู่มั้ย
```
ไฟล์ที่ลงท้าย `.BAD.json.xz` = ดึงมาได้แต่เนื้อในไม่ผ่านการตรวจ (เก็บไว้เป็นหลักฐาน ไม่ทิ้ง)

อ่านไฟล์:
```bash
xz -dc raw/2026/09/10/1405Z/okx_optsum_btc.json.xz | python3 -m json.tool | head
```

## ⚙️ กลไก
- `collect.py` — ดึง 16 endpoint (retry 3 ครั้ง · timeout 30 วิ) → ตรวจเนื้อใน → บีบ xz → เขียนลง `$OUT_DIR`
  - ตรวจเนื้อในจริง ไม่ดูแค่ HTTP 200 (OKX ตอบ 200 พร้อม `code!=0` ได้)
  - ล้มบางตัว → บันทึกใน `_meta.json` แล้วไปต่อ · **ล้มทั้ง 16 ตัว → job แดง** GitHub ส่งเมลเตือน
- `push_github.py` — ยัดไฟล์เข้า repo ผ่าน **Git Data API** (blob → tree → commit → ref)
  - ไม่ใช้ `git push` เพราะ repo จะโตขึ้นทุกวัน การ checkout ทั้งก้อนทุก 2 ชม. จะช้าขึ้นเรื่อยๆ
  - วิธีนี้เวลารันคงที่ ไม่ว่าคลังจะใหญ่แค่ไหน
- `.github/workflows/collect.yml` — cron `5 */2 * * *` (UTC) + ปุ่มยิงเอง (Actions → collect → Run workflow)

## 📈 ขนาดที่ต้องรู้ล่วงหน้า
วัดจากของจริง 10 ก.ย. 2026: ดิบ ~2.7 MB/รอบ → **บีบเหลือ ~250 KB/รอบ**
→ **~3 MB/วัน · ~90 MB/เดือน · ~1 GB/ปี**

⚠️ GitHub แนะนำให้ repo อยู่ใต้ 1 GB → **พอขึ้นปี 2027 ให้เปิด repo ใหม่** (`crypto-raw-2027`) แล้วชี้ workflow ไปที่ใหม่
คลังเก่ายังอ่านได้เหมือนเดิม ไม่ต้องย้ายข้อมูล

## ⚠️ ข้อควรรู้
- cron ของ GitHub Actions **มาช้าได้ 5–15 นาที** ในชั่วโมงที่คนใช้เยอะ — ไม่ใช่ปัญหาสำหรับ snapshot ทุก 2 ชม. แต่อย่าคาดหวังเวลาเป๊ะวินาที
- เวลาใน path เป็น **UTC** ทั้งหมด (บวก 7 = เวลาไทย)
- repo ที่ไม่มี commit เลย 60 วัน GitHub จะปิด schedule อัตโนมัติ — คลังนี้ commit ทุก 2 ชม. จึงไม่โดน
